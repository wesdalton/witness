# First live-tool auditor research cycle — 24 October 2026

Witness now has **24 completed autonomous audit episodes using live tools**.
Four of those episodes include Python/SQL written by the model and executed
against a database. This establishes an operational capability missing from the
October 18 pilot, whose checks retrieved prerecorded observations.

The ledger comparison did **not** show endorsements suppressing verification:
every agent inspected source and gave the correct verdict. The SQLite calibration
was also successful. These small, authored cases do not establish the proposed
communication–verification mechanism, nor its absence in other settings.

## Results

All runs requested `openai/gpt-6-luna` through OpenRouter, pinned to OpenAI, with
reasoning disabled, 1,024 maximum output tokens per response, provider sampling
defaults, no retries/fallbacks, and 3.2-second request pacing. Each episode had a
fresh context, eight effort units, and at most eight model responses.

The failed initial episode listed files, then requested three reads together.
The initial harness incorrectly required one tool per response and stopped.
The unexecuted reads are not counted. This infrastructure failure is retained;
three remaining planned episodes were never started. The revised harness accepts
tool bundles, validates their aggregate cost before execution, and charges each
action separately. No agent output was silently repaired or rerun in place.

The four arms in the ledger screen each contain two true and two false episodes.
Those are repeated executions of one case family, not independent task samples.
All start with identical passing-test reports across truth values. Peer statements
are authored experimental stimuli, not outputs from independently running peers.

## What the live executions did

In the ledger case, reading the actual shared date predicate (`<` versus `<=`)
settled the narrow endpoint claim. Agents did not need to execute Python to find
the answer. Their choice to use cheaper source evidence is not a verification
failure. Two honest episodes additionally ran the supplied tests in Docker.

The new SQLite case prevents source inspection alone from settling the aggregate.
The same report claims 43,210 cents in both conditions, while the submitted rows
sum to 43,210 or 42,310 for the specified account and inclusive date interval.
Each agent wrote a parameterized query, executed it through Python, observed the
actual returned sum, and supported or refuted the report accordingly. Review of
all four queries confirmed the correct account and both date bounds. The runner
did not provide a query, a prerecorded result, or a correct-answer label.

Example from a false-report episode, generated by the model:

```python
import sqlite3
con = sqlite3.connect('/workspace/records.sqlite')
cur = con.execute(
    "SELECT COUNT(*), SUM(amount_cents) FROM transactions "
    "WHERE account=? AND posted_on>=? AND posted_on<=?",
    ('ops', '2026-09-01', '2026-09-30'),
)
print(cur.fetchone())
# Actual live stdout: (5, 42310)
```

Execution used an unprivileged container with no network, a read-only case mount,
no provider credentials, limited processes/memory/time, and bounded captured
output. Each execution starts fresh. Separate reference checks run before paid
requests and remain outside the model's observation.

## Interpretation and next decision

This is one economical model, two authored case families, and a small number of
repeated runs. There is no independent-peer swarm, no population-level estimate,
and no treatment advantage demonstrated. The database calibration has no peer
comparison. The ledger screen is at a ceiling for source acquisition and accuracy.
The neutral-message control is approximately, not exactly, length-matched.

More fundamentally, unused effort has no competing payoff in these single-claim
tasks. The agent can afford to check, so this design cannot convincingly measure
communication displacing other useful verification work. Buying many more runs
would not repair that problem.

Stop inference on these configurations. The [next experiment](next-experiment.md)
will allocate a binding verification budget across competing claims. Build and
validate that environment for free before spending more on models. The
[decision log](decisions.md) records each gate, the improvements made, and the
reason for the next expenditure.

## Reproduce without spending

From the repository root:

```bash
.venv/bin/python -m pytest -q
.venv/bin/ruff check .
.venv/bin/python scripts/audit_agent_study.py
.venv/bin/python -m swarm_lab.agent_study \
  --stage calibration --family sqlite --out /tmp/witness-next-plan
```

The last command only prints a plan. `--live` is required for paid requests, and
existing output directories are rejected. Docker execution uses the existing
`sandbox-default:latest` image, resolved to an immutable image ID in each manifest.
It can be built from `sandbox/Dockerfile`; the recorded runs used Python 3.12.14
and pytest 8.4.1. Rebuilding a mutable base-image tag may change that environment.
Model reruns are stochastic and billable; auditing the saved records is local.

Final validation: 86 Python tests, 14 browser engine tests, lint, and all four
live reference cases passed. The artifact audit found no mismatched traces,
response IDs, usage records, or frozen source hashes. Its retained warning is the
missing full source snapshot for the first aborted calibration.
